# ADR-0006: stdlib sqlite3 with numbered SQL migrations instead of SQLAlchemy + Alembic

**Status:** Accepted · **Date:** 2026-10-24 · Amends [ADR-0002](0002-local-first-storage-and-queue.md) (migration tool only)

## Context
The Car stage (R-06…R-10) needs durable state: revisions, exports, jobs, job dependencies and job attempts. That is five small tables and about a dozen queries, written by one Agent process with one worker thread. ADR-0002 and the stack table in `AGENTS.md` §5 planned SQLAlchemy 2 + Alembic for this.

## Decision
- Use Python's built-in **`sqlite3`** module and plain SQL. No ORM.
- The database is one file per workspace: **`<workspace>/.pnp/state.db`**, in **WAL** mode with `foreign_keys = ON` and a 10 s busy timeout. Each thread opens its own connection.
- Schema changes are **numbered SQL files** in `pnp_agent/migrations/` (`0001_initial.sql`, `0002_….sql`, …). `PRAGMA user_version` stores the last applied number. On start, `init_db` applies each newer file in its own transaction together with the version bump, so a crash never half-applies one. Files are never edited after they ship; a change is a new file.
- All job SQL lives in one module (`pnp_agent/job_store.py`), so a later Postgres store for server mode replaces one file.

## Consequences
- ✅ No new dependencies; nothing to configure or generate; migrations are readable SQL.
- ✅ The queue needs SQLite-specific behaviour anyway (`BEGIN IMMEDIATE` to claim a job, WAL), which an ORM would only wrap.
- ⚠️ No autogenerated migrations or downgrade scripts. Acceptable for ~5 tables; a downgrade is "delete `state.db`" in local mode (artifacts and revisions stay on disk).
- ↩️ Server mode (Postgres) will revisit this; SQLAlchemy can come back then if a second store really needs it.
